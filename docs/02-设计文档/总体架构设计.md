# OpenTenBase pgvector 查询路径总体架构设计

## 1. 系统上下文

本项目把“数据、查询、执行计划、源码补丁、证据报告”组成一条可重建链路：固定 item/query 数据进入 OpenTenBase Coordinator/Datanode；单长连接 harness 发送同一批查询；exact 与 IVFFlat 结果用于 recall 校验；执行计划、临时块和 perf 记录进入 CSV；补丁系列改变 pgvector/OpenTenBase 的查询路径；报告脚本只从归档数据生成图表和 PDF。

```text
固定数据 + 查询 CSV
        │
        ▼
OpenTenBase Coordinator ──> Datanode / pgvector IVFFlat
        │                         │
        ├─ EXPLAIN/回归计划       ├─ exact 与近似 top-k
        ├─ workload 日志          └─ perf / temp blocks / RSS
        ▼
原始 CSV + SHA256 + claim_validation.md
        │
        ▼
图表脚本 ──> PDF 报告 ──> PR / 上游投递包
```

## 2. 模块划分

| 模块 | 责任 | 关键边界 |
|---|---|---|
| 数据合同 | 固定 rows、dims、seed、queries、top-k | 变更必须创建新 run |
| 计时与执行 | 长连接、ABBA 顺序、计划和负载快照 | 不把客户端 fork 开销当查询延迟 |
| 正确性 | exact/IVFFlat top-10、L2/IP/Cosine/iterative regression | recall 不下降是硬门槛 |
| rescan 生命周期 | 查询值清理、tuplesort 批次状态 | OpenTenBase PG10 用销毁/重建恢复等价语义 |
| 构建链修复 | 恢复 pgvector 已有 CFLAGS/自动向量化 | 不写手工 SIMD intrinsics |
| 辅助调优 | `ivfflat.query_work_mem` | 7.32% 低于 10% 门槛，不作主成果 |
| 报告管线 | CSV → SVG/PNG → PDF | PDF 不是数据真相源 |

## 3. 数据流与控制流

数据先经过固定 seed 生成和 SHA256 清单，再建立同参数索引。每次 workload 先 warm-up，再按 ABBA 交错运行 scalar/vectorized 变体；每个重复保存完整耗时、200 个 index loops、临时块和动态库身份。exact 查询提供 top-10 参照，近似查询提供实际输出；两者排序后逐行比较。报告阶段不重新计算业务数字，只读取 `report/figures/data/` 快照。

## 4. 优化方案决策

本阶段正式选定候选 E：恢复 OpenTenBase in-tree 构建链对 pgvector 既有自动向量化参数的传递。选择理由是源码和汇编都能验证，变量只涉及构建标志，且 5 次 ABBA、recall 和 perf 三条证据同时通过。它不改变算法、数据、probes 或距离函数。

rescan 生命周期修复是必要的正确性前置；query-specific memory 是辅助控制。分布式 top-k over-fetch、`ivfflatcostestimate` 代价模型、迭代扫描分片行为和过滤后置放大仍是 W3 候选，尚未取得本 run 的门禁证据，不进入当前优化结论。

## 6. 运用途径

DBA 可用复现命令检查同一版本的计划和结果；维护者可用五件套 format-patch 审查单个变更；评审者可从原始 CSV、动态库哈希和 PDF 图表反向追溯。任何跨硬件、跨距离或分布式使用都必须复制数据合同并创建新 run。
