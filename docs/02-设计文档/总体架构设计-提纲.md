# 总体架构设计（提纲・方向一）

> 回答：系统怎么搭、模块怎么分、数据怎么流、谁在什么场景用它、每条 RQ 落在哪个模块。

## 1. 系统上下文

```
SIFT1M/GloVe 数据集 ──加载──> OpenTenBase(CN──DN, pgvector 0.8.0)
                                   ▲
bench/ 脚本（单长连接 + 服务端计时）─┘
     │
     ├─ recall/latency 结果 CSV ──> metrics.sh ──> Pareto 前沿图
     └─ EXPLAIN ANALYZE 计划证据 ──> 计划核对（是否命中索引、是否下推 DN）
patches/ 优化补丁 ──作用 on──> pgvector/OpenTenBase 执行器
```

## 2. 模块划分（对齐 R002 §2.1 的 bench/ 目录）

| 模块 | 职责 | 关键设计点 |
|---|---|---|
| datasets/ | 数据获取与校验 | fetch + SHA256；均匀随机=负向对照 |
| 计时引擎 | 延迟测量 | 单长连接 + `EXPLAIN (ANALYZE, TIMING ON)`；`SELECT 1` 自测开销 |
| 指标计算 | recall@k、p50/p95/p99 | ≥1000 样本上的分位数 |
| 报告生成 | CSV → 图表 → 对比报告 | 结果带时间戳与配置快照 |
| 优化补丁 | W3 优化候选实现 | 见 §4 |

## 3. 数据流（成稿时画正式图）

数据集 → 建表/建索引（lists 按官方公式）→ warm-up → 查询批（approx 与 exact 对照）→ 指标汇总 → 图表。

## 4. 优化方案架构（W3 选定后填充）

候选 A 分布式 top-k over-fetch：CN 归并策略、k'=f(k,N) 的设计空间与实验设计。
候选 B 代价模型修正：`ivfflatcostestimate` 的修改点与交叉点实测设计。

## 5. 应用途径（实际运用场景）

- DBA/使用者：给定数据规模与 recall 目标，选 lists/probes（消费 RQ-104/201 的结论）。
- 上游贡献者：可复现基线，用于验证未来 pgvector/OpenTenBase 改动的性能影响。
- 本课题：官方「优化 PR」的验证载体。
