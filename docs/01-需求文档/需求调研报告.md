# pgvector 查询性能优化需求调研报告

## 1. 调研结论

本项目的需求不是“让数据库跑一个漂亮的 benchmark”，而是解决 OpenTenBase 内置 pgvector 在真实查询链路中的两个可复现问题：重复 IVFFlat rescan 的生命周期与排序状态不稳定，以及构建链静默丢失上游已有自动向量化编译参数。前者会在嵌套循环中进入 `invalid tuplesort state`，后者让内积计算退回标量指令。两条问题都能由源码、回归日志和固定 workload 交叉验证。

需求边界也必须诚实。当前证据覆盖单机、Cosine、高 `probes`、200 条固定查询；没有把均匀随机数据当作 ANN 排序优越性的证明，没有把缺少 P95/P99 的均值结果写成尾延迟结论，也没有把尚未完成的分布式分片矩阵写成已解决问题。

## 2. 调研方法

调研按四层进行：一是核对 pgvector/OpenTenBase 源码和构建文件，确认问题的机制位置；二是查看上游 issue/PR 与公开部署资料，判断问题是否具有生态意义；三是把候选需求转成可验收的 RQ；四是只用本仓库的固定数据、原始日志和提交补丁验证已实现需求。外部资料作为背景和设计约束，不替代本项目的第一手实验。

## 3. 用户场景与痛点

| 场景 | 用户看到的现象 | 需要的能力 | 本仓库证据 |
|---|---|---|---|
| 重复查询/嵌套循环 | rescan 后排序状态错误，或执行期内存增长 | 生命周期正确性与峰值观测 | `artifacts/.../claim_validation.md`、rescan 回归 |
| 高 probes 检索 | 结果正确但内积计算占据大量 CPU | 找到热点并恢复已有编译能力 | scalar/vectorized perf 报告 |
| 构建参数变化 | 同一 pgvector 代码在 OpenTenBase 构建链上没有 packed SIMD | 构建标志可追溯、可复现 | Makefile 补丁与汇编证据 |
| 调优评审 | 单次快跑无法说明收益是否稳定 | 交错重复、变体哈希、原始 CSV | `run_manifest.json`、ABBA 矩阵 |

## 4. 生态与对标

pgvector 已被 AWS RDS、Supabase、Neon、Azure 等 PostgreSQL 生态采用，因此查询路径问题会影响一批以 PostgreSQL 为向量检索入口的用户。本报告不把某个动态 GitHub star 数或市场规模当作性能验收依据；调研存档中的市场数字来自不同口径，存在差异，只作为“需求不是单一产品特例”的背景。

开源 ANN 对标通常使用 recall-QPS 前沿和固定 ground truth。均匀随机高维向量适合测试数据管线和代码连通性，却不能支撑不同算法排序结论，所以本项目把历史均匀随机图移入附录，并在主结论中使用固定 workload 的逐行正确性与机制证据。AlloyDB 的专有诊断能力说明用户确实需要 recall/性能解释，但本项目不声称复制专有系统，只交付 OpenTenBase 可审计的源码和实验链。

## 5. OpenTenBase 特有空白

上游 pgvector 具备自动向量化设计和较新的 tuplesort 生命周期语义，但 OpenTenBase PG10 基座的 in-tree 构建与 API 组合不同。源码审计发现：`PG_CFLAGS` 没有进入实际编译行，导致已有自动向量化参数静默失效；同时 OpenTenBase 没有上游 `tuplesort_reset()`，需要用销毁并重建排序状态恢复等价批次语义。这是平台适配问题，不是另写一个 ANN 算法的问题。

## 7. 需求结论

需求分成三层：第一层是正确性与生命周期，第二层是构建链可复现和高 probes 性能，第三层是跨距离、并发和分布式拓扑的扩展验证。本仓库已完成前两层的一个可审计闭环；第三层进入后续需求，不用当前单机结果冒充普适结论。下一份需求规格说明书把每条需求绑定到验收门禁、证据路径和当前状态。
